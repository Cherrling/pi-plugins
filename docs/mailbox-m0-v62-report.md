# Mailbox v6.2：M0 本地边界验证

日期：2026-09-20。环境：Linux、Python 3.14.7。

**结论：⑥⑦⑧ 的策略原型验证通过；⑨ 复现两个反例，v6.2 的短写规则尚未闭合。** 候选修正“每发送者锁覆盖整个补写过程 + 显式隔离残尾”已在原型验证。没有修改生产 pi 插件、真实 mailbox 或 Codex 配置，整体 M0 尚未放行。

## 测试范围

这是独立 Python 策略原型，不是尚未实现的 Node mailbox-core。使用真实临时文件、`flock`、`O_APPEND`、原子 rename、子进程与 `SIGKILL`。短写通过限制每次传给 `os.write` 的字节数注入；磁盘满通过在部分字节已落盘后注入 `ENOSPC` 模拟。

接收输出写入本地文件，代表“已输出”，不代表宿主确认。消息采用固定测试 ID，seen 保存完整 ID 集合；没有验证 SAMP hash、时间戳水位线、别名生命周期、Node 锁实现、真实 hooks 或断电持久性。因此下面的“通过”均指策略原型，不代表生产实现已经验收。

## 结果

| 项目 | 实测 | 结论 |
|---|---|---|
| ⑥ 十条积压、不新增写入 | 每次两条，五次投完；达到限额不消费时 backlog 保持；日志摘要不变 | 原型通过 |
| ⑦ 输出后、状态提交前杀进程 | 下次检查重新输出两条；进程死亡释放读者锁 | 原型通过，预期可能重复 |
| ⑦ 状态提交后杀进程 | 下次检查跳过；显式 replay 后两条恢复；日志摘要不变 | 原型通过，确认尽力投递窗口仍存在 |
| ⑧ 全部读完后单条／全部 replay | 日志 fingerprint 完全不变，仍能分别重投一条／四条 | 原型通过 |
| ⑧ check 与 replay 并发 | check 持锁读状态时 replay 实际遇到锁冲突并等待；旧 check 完成后 replay 生效 | 原型通过，未丢重放意图 |
| ⑨ 无发送者锁的循环补写 | A 前缀 → B 完整行 → A 剩余；最终两行均无法解析 | **方案反例复现** |
| ⑨ 失败残行后正常追加 | A 残片 + B 完整行，拼成一个坏行；B 虽完整写入仍不可读 | **方案反例复现** |
| ⑨ 候选修正：发送者锁 + 残尾分隔 | 失败发送报错，保留残片；下一发送先隔离残尾；后续两条完整消息可读 | 候选修正在原型通过 |
| ⑨ 候选修正并发补写 | 四个真实进程、共 100 条，每次只写 7 字节；最终 100 条唯一记录、零坏行 | 候选修正在原型通过 |

## ⑨ 为什么仍不成立

`O_APPEND` 的原子步骤覆盖一次系统调用，不覆盖一个由多次调用组成的补写循环。无发送者锁时，以下调度合法：

```text
A: write(A 的前 12 字节)
B: write(B 完整 JSON + 换行)
A: write(A 剩余字节 + 换行)
```

测试得到两条不可解析的行，A、B 都无法被正常扫描。这不是读取方跳过坏行能修复的：跳过只会让有效消息 B 也被忽略。

第二个反例不需要并发。A 写入前缀后失败，关闭文件不撤销已写字节。下一发送者直接追加 B，B 就接在 A 残片后面。**“下次正常追加自行隔离”缺少实际隔离步骤。**

建议把 §2 约束补成：

1. 同一发送者的所有写入入口使用同一个稳定锁文件；持锁覆盖尾行检查、恢复和整个补写循环。不同发送者仍可并发。
2. 发现尾部没有换行时，先在锁内追加分隔换行，保留残片并报告坏行；完成隔离后才写新记录。隔离失败则拒绝本次发送，不得继续追加正文。
3. 部分写入后再次失败，返回发送失败，保留已写残片；不要把“丢弃”理解成自动撤销文件中的字节。下一次写入仍先检查残尾。
4. 补写遇到零进展或错误必须退出；发送成功只在完整记录（含换行）写入后返回。断电持久性不在本轮保证内。

原型按以上规则验证了后续消息不受失败残片污染；它没有保证失败消息自动重发，也没有实现业务动作幂等性。

## 后续验收边界

- 将候选写入修正规则落实到正式方案与 Node core，再用相同用例验收实际实现。
- 真实 Codex 的 M0 ①②③⑤，以及完整 check 性能 ④，本轮没有执行；旧性能基线不能当作 v6.2 完整路径成绩。
- replay 的幂等性需要由任务执行层单独处理；清除 transport seen 以重投，并不保证任务副作用不会重复。
- 原型选择完整 seen ID 集合。若正式实现改用 `ts + 最大时间戳处的 ids`，需要另测历史单条 replay、晚到消息和时间回退，不能直接沿用本轮结论。
